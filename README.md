# Отчёты отдела — рабочая сборка

Данные пересчитаны на полной users «юзерс актуаааальный самый.csv» + metrics с lag + бонусах. Срез факта: 30.09.2026. 124 игрока metrics без профиля показаны как UNKNOWN в общих агрегатах и исключены из когорт/retention.

## Просмотр
Откройте index.html. HTML самостоятельные, графики работают без CDN и интернета. CRM использует crm.js и crm.css, поэтому держите файлы вместе. В архиве плоская структура: папки переносить не нужно.

## GitHub и Streamlit — плоская загрузка без папок
1. Распакуйте ZIP на компьютере. Сам ZIP в GitHub не распаковывается.
2. Откройте папку с распакованными файлами, выделите нужные файлы из списка внизу и загрузите их через Add file → Upload files в корень репозитория. Сами папки и папку data создавать не нужно.
3. Не загружайте исходные CSV. Срезы уже встроены в HTML.
4. В Streamlit укажите app.py как Main file path.
5. Для локального запуска: python -m pip install -r requirements.txt, затем python -m streamlit run app.py.

Файлы сайта в этом комплекте значительно меньше лимита GitHub Browser (25 MiB на файл). Исходные метриксы с лагами около 34 MB превышают этот лимит; бонусная выгрузка ещё больше. Исходные player-level данные не входят в репозиторий.

В рабочей среде этого выпуска Streamlit не установлен, запуск сервера не проверен. Проверены расчёты и исполнение логики вкладок JavaScript; полноценная браузерная визуальная проверка пока не выполнена.

## Разделы
Главная: план–факт, градиент выполнения, октябрьские планы, ссылки и алерты.
Пульсация: деньги, DAU/MAU, новые регистрации/FTD, новые активные, продолжающие активность, короткие возвраты, реактивации, чарн; детализация бонусных выдач.
Ретеншен: Return On or After и Return On от ставки/FTD, дневная зрелость или единая D30 база; интервалы D1–3 / D4–7 / D8–14 / D15–30; месячные регистрационные когорты с регистрациями, FTD и подтверждёнными контактами; воронка D7/D30 с общей и пошаговой конверсией.
Долёты: FTD в месяце позже регистрации, планы, когорты, задержки, воронка и экономика D30.
Реактивация: дневные базы и возвраты, структура неактивности и сравнение GEO.
CRM: ранее согласованный макет, контрольные группы и карточка эксперимента без вымышленных данных.

## Расчёты и границы
- Факт заканчивается днём до --as-of, но не позже последнего дня metrics. Текущий срез: 30.09.2026.
- Активность — bet_cnt > 0 ИЛИ deposit_cnt > 0. Bonus-only строки не активность.
- Полные неактивные дни до возврата = activity_date − previous_active_date − 1. Соседние активные дни дают 0, это продолжение активности.
- Категории: 1–7, 8–14, 15–30, 31–60, 61–90, 91–180, 181+ дней. «Чарн» здесь — 8+ дней; короткая пауза 1–7 показана отдельно. Это рабочий порог отчёта, а не универсальное определение бизнеса.
- На начало дня D база содержит всех с подходящей паузой на конец D−1, включая вернувшихся в D. Дневной процент = возвращения из категории / её база на начало дня.
- Суммарная частота периода = сумма возвратов / сумма дневных баз. Это не процент уникальных вернувшихся за месяц.
- LAG сверяется с наблюдаемой историей. Предыдущие даты до окна добавляют начальные интервалы неактивности. Игроки без единого события в окне могут отсутствовать; для абсолютного чарна нужна полная начальная база last_active_before_period.
- Верификация = email_verified_flag OR sms_verified_flag. Это не KYC; состояние на момент выгрузки.
- Retention after FTD = ставка или депозит. Интервалы используют полностью завершённые окна и показывают знаменатели.
- Линия от ставки использует первую ставку наблюдаемой истории только для регистраций внутри этой истории. Нужна проверка SQL: включены ли bonus-money bets, соответствует ли это Any money bet в Amplitude. Окна календарные, а на скрине Amplitude — скользящие 24 часа; точного совпадения без времени событий нет.
- Rolling учитывает возврат на Dn или позднее до среза, в том числе после D30. Возраст когорт влияет на результат, поэтому rolling исключён из алертов.
- Депозитная воронка рассчитана из metrics в фиксированных D0–D7 и D0–D30; lifetime snapshot не смешивается с завершёнными окнами.
- GGR и NGR используются из metrics. Пропуски финансовых полей отмечены; суммы — известная часть. NGR уже содержит Bonus cost: второй раз его не вычитать.
- Бонусный файл: выдачи по created_dttm, состояние на дату экспорта. changed_dttm не является надёжной датой перевода; расходы по датам берутся из metrics.
- Выводов средств в источниках нет. Withdrawal и net deposits не выдумываются.
- Основные GEO — TR, AR, CO, IN. Другие выбираются отдельно. UNKNOWN = финансовая строка без профиля; такие операции не теряются.

## Ежедневное обновление
Вне Streamlit (на сервере/Airflow) сохраните выгрузки users.csv, metrics.csv, bonuses.csv. Для ПОЛНОЙ users:

python refresh.py --users users.csv --metrics metrics.csv --bonuses bonuses.csv --users-complete --as-of 2026-10-01

Если временно используется ограниченная users, можно явно дополнить её прежним полным реестром:

python refresh.py --users users.csv --metrics metrics.csv --bonuses bonuses.csv --registry user_lifecycle.csv --as-of 2026-10-01

Второй вариант только переходный: старый реестр не гарантирует полноты регистраций последующих дат. Не используйте --users-complete для отфильтрованной выборки.
После успешного расчёта публикуйте изменённые HTML и dashboard_data.json одним коммитом/деплоем. План хранится в targets.csv, ручные факты — manual_facts.csv. render_html.py позволяет применить изменение планов без повторного чтения больших выгрузок.
Никакие задания Airflow, подключения GitHub или автоматические публикации в этой сборке не созданы.

## Как хранить предыдущую активность
Колонки previous_active_date и days_since_previous_active_day допустимы: в присланном файле около 34 МБ. Вторая колонка производная и может быть рассчитана на этапе обработки.
LAG должен считаться по всей истории активных дней, а ограничение выгрузки по дате — после расчёта LAG. Лаг по всем финансовым строкам, включая bonus-only, неверен.
Для полной базы чарна нужна отдельная начальная таблица player_id, last_active_before_period, geo для всех ранее активных игроков, включая тех, кто не вернулся в периоде. Последнюю активность из текущей users нельзя использовать как историческую на произвольную дату: это утечка будущего.
